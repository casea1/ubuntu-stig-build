GR - Ubuntu 24.04 Imaging Guide

Audience: Grand Rapids DT. No Linux experience required.
Time: 2–3 hours, most of it unattended. Add about an hour per FPGA toolchain.

Sections A through E apply to every machine. Section F applies only to engineering workstations that need the FPGA tools. Follow the steps in order and do not skip any. If a step fails, check Common Issues at the end, then escalate.

Which Profile Am I Building?

Confirm the profile with the requester before you start. It changes one command and whether you do Section F.

ProfileUsed forUSB installerBuild command in step 15Section F (FPGA)
developmentEngineering workstationsServer| sudo bashYes
emiEMI, classified-capableDesktop| sudo PROFILE=emi bashNo
emi-unclassEMI, unclassified onlyDesktop| sudo PROFILE=emi-unclass bashNo
aiAI serversServer| sudo PROFILE=ai bashNo
baselineHardening a machine that already existsn/a, already installed| sudo PROFILE=baseline bashNo

Use Ubuntu Server for everything except the two EMI profiles. On development the build installs the graphical desktop and the remote desktop server itself, so a Server base ends up with a full GUI. The EMI profiles do not install a desktop, so those two need the Desktop installer, which already has one.

Getting this wrong is not a small thing. An EMI machine built from the Server installer has no desktop and nothing in the build adds one.

Before You Start

  • Ubuntu 24.04 USB installer, Server or Desktop according to the profile table above
  • Ubuntu Pro token
  • A LUKS passphrase for this machine
  • The assigned hostname
  • The profile from the table above

A. Firmware Settings

  1. Power on the machine and enter BIOS / UEFI setup.
  2. Set boot mode to UEFI. Do not use Legacy or CSM.
  3. Set Secure Boot to ON.
  4. Disable deep sleep (S3 / "Suspend to RAM"). Depending on the vendor this is Block Sleep, Deep Sleep Control, or a Sleep Mode set to Windows/S0ix rather than S3.
    • A machine that suspends to RAM holds the disk encryption key in memory while it sits there, and this build is set up to lock and unlock at boot, not across a suspend.
  5. Set a BIOS/UEFI administrator password and record it on the build sheet.
    • Use the standard temporary imaging password. Like every credential set during imaging, it is replaced at deployment.
    • Without it, anyone can re-enable deep sleep, turn off Secure Boot, or change the boot order and start the machine from their own USB drive.
  6. Move the USB drive to the top of the boot order, then save and exit.

Everything you set during imaging is temporary. The BIOS password, the LUKS passphrase, and the overlord account password are all replaced at deployment. Record them on the build sheet and hand it over with the machine.

B. Install Ubuntu

  1. Boot from the USB drive and start the installation.
    • Server: choose Try or Install Ubuntu Server, then accept the defaults through language, keyboard and network. Take the network offer, the machine needs it in Section C.
    • Desktop: choose Install Ubuntu.
  2. Set up the disk. The wording differs between the two installers, the result is the same: one encrypted LVM disk.
    • Server: at Guided storage configuration choose Use an entire disk, then tick Set up this disk as an LVM group and Encrypt the LVM group with LUKS.
    • Desktop: at Installation type choose Erase disk and use LVM, then tick Encrypt the new Ubuntu installation.
  3. Enter the LUKS passphrase. Use the temporary imaging passphrase and write it on the build sheet.
    • It is changed at deployment with sudo it-luks-passwd, which asks for the current passphrase and then the new one. The TPM auto-unlock keyslot is separate and is not disturbed, so the machine keeps unlocking itself at boot.
    • it-luks-rebind is for a different fault, a stale TPM binding after Secure Boot or firmware changed. It is not needed after a passphrase change.

    WARNING: Losing the passphrase while the TPM binding is also gone leaves the disk unrecoverable. Either one alone is survivable, but do not leave this step without the passphrase written down.

  4. Set the account name to overlord, exactly. Lower case, no spaces. The Server installer calls this your username, the Desktop installer calls it your name.
    • This is the account the build tools expect. A different name sends this machine's permissions to an account nobody can sign into.
    • Do not use a personal account name here.
  5. Set the computer name to the assigned hostname. The Server installer calls this your server's name. Do not leave it as ubuntu.
    • Server only: when it offers to install the OpenSSH server, say yes. It is how you reach the machine from the lab, and it is what WinSCP connects to in Section F.
  6. Complete the installation, remove the USB drive, reboot, and sign in as overlord.
    • A Server build signs in at a text console, with no desktop. That is correct at this point. The build installs the desktop in Section C.
  7. Connect the machine to the network. Leave it connected until Section D is complete.

C. Run the Build

  1. Open a terminal and install the lab certificate: 
    sudo curl -fsSLo /usr/local/share/ca-certificates/lab-root-ca.crt \
  http://git.asplab.com/lab-root-ca.crt

sudo update-ca-certificates
  2. Start the build. Use the command for this machine's profile from the table above. The development profile is shown here: 
    curl -fsSL https://git.asplab.com/ASPLAB/ubuntu-stig-build/raw/branch/main/bootstrap.sh | sudo bash
  3. When prompted, paste the Ubuntu Pro token. Nothing appears on screen while you type. This is expected.
  4. When prompted, enter the LUKS passphrase, so the disk unlocks automatically at boot.
  5. Monitor the build. It runs a long time and goes quiet for long stretches. That is not a failure. 
    sudo journalctl -u stig-build -f
  6. Wait until the build reports active (exited): 
    systemctl status stig-build

D. Verify Sign-In, Then Reboot

WARNING: Do not skip step 20. The build rewrites the sign-in configuration. If sign-in is broken and the machine is rebooted, it must be rebuilt from a USB drive.

  1. Leave your current terminal open. Open a second terminal window and run both commands: 
    sudo -v

sudo pam-auth-check
    • Both succeed: continue to step 21.
    • Either fails: stop and escalate. Do not reboot.
  2. Reboot the machine: 
    sudo reboot
  3. Sign in again. The sign-in screen displays the DCSA banner.

E. Verify Hardening

This is the part of imaging that matters. A machine that boots is not a machine that is hardened. Work through every check below and do not release the machine until each one passes.

E1. Overall status

  1. Run the status overview: 
    sudo it-status
  2. Confirm FIPS mode is active: 
    uname -r

cat /proc/sys/crypto/fips_enabled
    • uname -r must end in -fips
    • The second command must return 1
    • If either is wrong, see FIPS did not enable in Common Issues

E2. The organization checklist

  1. Run the checklist. It prints one line per item. 
    sudo it-checklist
  2. Read every line. Items marked FAIL must be resolved or recorded before the machine is released.
    • Item 6 checks the audit rules actually loaded into the kernel, which is a common silent failure. It must not report a fault.
    • An item that says a manual step is outstanding (GRUB password, license server) is expected at this stage. Note it and continue.

E3. The compliance scan

  1. Run a full OpenSCAP scan against the DISA STIG profile. This takes several minutes. 
    sudo it-oscap
    • An exit code of 2 is normal. It means the scan ran and some rules failed, which is expected on any real system.
  2. Confirm the scan wrote its results: 
    ls -l /opt/ia/oscap/manual/
  3. Generate the STIG checklist from that scan, for the compliance record: 
    sudo it-ckl
  4. Confirm the checklist file was produced: 
    ls -l /opt/ia/stig/checklists/
  5. Copy the reports off the machine while it is still on the network. They are in /opt/ia/.
    • /opt/ia/usg/: the USG audit report
    • /opt/ia/oscap/: the OpenSCAP scan results
    • /opt/ia/stig/checklists/: the STIG checklist

E4. Sign-in check

  1. Confirm the DCSA banner appears at the sign-in screen and that overlord can sign in after a reboot.

Account passwords for engineers and auditors are not set during imaging. They are set at deployment, using the deployment checklist.

E5. Record the machine on the HW/SW list

  1. Generate the inventory, then open it: 
    sudo it-inventory

cat /opt/it/inventory-$(hostname -s).txt
  2. Copy these onto the HW/SW list:
    • Service tag, under System. This is the serial on the sticker; on Dell it is the service tag.
    • Disk serial numbers, under Storage, the SERIAL column. Record one row per drive with its model and size. If the machine has more than one drive, record all of them.
    • The hostname and MAC address, if your list has columns for them.

    Re-run sudo it-inventory after the last reboot. The file it writes is what an assessor is shown, and it is what checklist item 16 looks for.

F. FPGA Toolchains: development Profile Only

Skip this entire section for emi, emi-unclass, ai and baseline machines. They do not use these tools.

F1. Copy the installers

  1. From a Windows machine in the lab, open WinSCP and connect to this workstation over SFTP, signing in as overlord.
  2. Copy the Xilinx and Libero installers from the file server directly into: 
    /opt/it/installers/
    • If WinSCP reports a permission error writing there, see Cannot write to /opt/it/installers in Common Issues.
    • Use the offline installers. The web installers download during setup and will not work on a deployed machine.
  3. Make the installers runnable: 
    sudo chmod a+rx /opt/it/installers/*.bin

F2. Xilinx (Vivado)

  1. If you are using the web installer, generate the AMD token first. It needs an AMD account and internet, and must be run with sudo: 
    sudo /opt/it/installers/xsetup/xsetup -b AuthTokenGen
    • Skip this step when using the offline installer.
  2. Start the installation. It runs about an hour. 
    sudo it-fpga install xilinx

sudo journalctl -u xilinx-install -f

F3. Libero

  1. Prepare the install. It prints the exact command to run next. Use that command. 
    sudo it-fpga install libero
    • The first time this runs on a machine it builds a library Libero needs and Ubuntu does not ship, which takes a minute and needs the network. Do this before the machine leaves the lab.
  2. Run the printed command as your own user, without sudo. Under sudo the installer cannot open a window and fails.
  3. In the installer, set:
    • Install directory: /opt/microchip/Libero_SoC_2025.1
    • Common IP vault: /opt/microchip/common
    • Installation type: Full
    • Decline the post-installation script when offered
  4. When it finishes, return ownership of the folder: 
    sudo it-fpga fixup

F4. Finish the toolchains

  1. Configure the license server: 
    sudo it-fpga license --server 1702@licsrv
  2. Connect each programmer cable and authorize it: 
    sudo it-usb enroll
  3. Run the final toolchain check. All items must report OK. 
    sudo it-fpga status

Common Issues

The build failed and stopped part way

Read the last 40 lines of the log and escalate with them. The machine is not usable until the build completes.

sudo journalctl -u stig-build -n 40 --no-pager

FIPS did not enable

uname -r does not end in -fips, or /proc/sys/crypto/fips_enabled is 0. Check whether the FIPS service is on:

pro status | grep fips

If it is not enabled, try again. This step sometimes times out reaching Canonical:

sudo pro enable fips-updates

Reboot afterwards. If it fails repeatedly, escalate; do not release the machine.

Cannot write to /opt/it/installers over WinSCP

That folder is restricted to administrators. Confirm you are signed in as overlord and not a personal account. If it still fails, create a folder in your home directory, upload there, then move the files:

sudo mv ~/Libero*.bin ~/FPGAs*.bin /opt/it/installers/

"could not extract" when installing Xilinx

The installer file has no execute permission. Fix it and run the install again:

sudo chmod a+rx /opt/it/installers/*.bin

Libero installer says "could not connect to display"

It was started with sudo. Run the command exactly as sudo it-fpga install libero printed it, as your own user, with no sudo in front.

Libero says "No write permission for the selected directory"

The build has run since you prepared the folder and took ownership back. Prepare it again, then restart the installer:

sudo it-fpga install libero

Sign-in is slow, the screen is black, or the machine boots slowly

These usually share one cause and one fix. Run the repair tool, which reports first and changes nothing until you tell it to:

sudo it-repair

sudo it-repair fix

Then sign out and back in. Reboot to see the boot-time change.

If a session is still stuck at a black screen afterwards, sign in over SSH from another machine and reset that user's session:

sudo it-rdp status

sudo it-rdp reset overlord

Do not restart the remote desktop service. It disconnects everyone on the machine and breaks their next sign-in.

Libero will not start: "libpng15.so.15: cannot open shared object file"

The library Libero needs was never built on this machine. Normally sudo it-fpga install libero does it, but that step needs the network. Build it while the machine is still on the lab network:

sudo it-fpga compat build

An engineer asks how to open their browser IDE

They do it themselves, with no admin help. Tell them to click IDE (in a browser) in the applications list, or run:

my-ide

It shows their address and password. It runs while they are signed in and stops when they sign out, which is intended. There is nothing to set up during imaging.

A programmer cable is plugged in but not detected

USB devices are blocked until authorized. Enrol the cable:

sudo it-usb enroll

A config file prompt appears during updates

Choose N, which keeps the currently-installed version. The build's own configuration must be preserved.
